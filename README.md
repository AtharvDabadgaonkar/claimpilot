# 🛡️ ClaimPilot — AI Claims Triage, Automation & Governance

**Auto insurance claims arrive faster than adjusters can work them. Triaging every
claim by hand is slow and expensive; automating payouts without controls invites
claim leakage and unfair outcomes.** ClaimPilot takes auto claims in digitally,
scores each one for severity, complexity and fraud signal, fast-tracks the simple
ones, assists adjusters with the rest, and makes every AI decision explainable,
fair-tested and auditable.

Built for the fictional carrier **Northwind Mutual**. `Intake → Triage → Route → Assist → Govern → Measure`

## The core tension

Three things pull against each other, and the whole product is about holding them
in balance:

| Pull | What it wants | What it breaks |
|---|---|---|
| **Speed & automation** | Pay simple claims in minutes, not weeks | Overpays claims nobody checked |
| **Claim leakage** | Scrutinise everything, pay only what's owed | Slow, costly, poor customer experience |
| **Fairness & compliance** | Consistent, explainable, non-discriminatory outcomes | Constrains how aggressively you can automate |

Two product rules fall out of that, and they are enforced in code:

1. **The system can auto-approve, but it can never auto-deny.** Every potential
   denial goes to a human. There is no code path to an automatic denial, and a
   test asserts it.
2. **Protected characteristics are never model inputs** — but outcomes are still
   tested across those groups, because excluding a field does not guarantee a
   fair result.

### Three numbers that need explaining

**100% extraction accuracy is not a production figure.** The narratives
were generated from templates and the regular expressions were written against
those templates, so the number is close to circular. The hand-written
paraphrase set in `tests/fixtures/` was *also* used while tuning, which means
no genuinely held-out evaluation exists — every piece of text here is
synthetic. Read it as "the regression suite passes", not as evidence the
extractor would survive real claimant writing.

**Trust the cross-validated AUC (0.741), not the test-split AUC
(0.803).** The gap between them says the single split is flattering.
And precision is optimistic regardless: at a 25% base rate, roughly
10–25× a real auto book, a fraud model looks far better than it would in
production.

**The 8% STP rate is a property of this dataset, not the design.** Most
claims here are large (median ~$58k) and a quarter carry the reported-fraud
flag, so they fail the low-severity or low-fraud test. A real auto carrier
would fast-track a much larger share.

**On the override rate.** It counts only decisions where the AI made a
*substantive* call — a fast-track approval or an SIU referral. Routing a claim
to an adjuster queue is the AI saying "a human should look at this", so
whatever the adjuster then decides, nothing was overridden. Counting those
inflated the rate to 85% and made the metric meaningless.

**On the deadline breach rate.** 72% of claims have blown the
30-day decide clock, which looks alarming and is mostly an artifact: the
dataset's losses run Jan–Mar 2015 and the demo views them from a fixed date of
2015-03-15. The acknowledge deadline is met on 100% of claims because
digital FNOL acknowledges on submission.

### 🚩 This portfolio fails its own fairness check

**5 of 8 disparate-impact tests fall below 0.8**, and the
project reports that rather than hiding it. The worst is the STP fast-track
rate by age band at **0.3549** — the oldest band is fast-tracked at roughly
a third the rate of the highest band.

Age is **not a model input**. The disparity arrives by correlation: that band
has the fewest low-severity claims and the highest reported-fraud rate in this
data, so it fails the low-severity and low-fraud gates more often. And the
fraud label is a *reported* flag, so historical bias in who got referred is
reproduced.

That is the entire argument for outcome testing: **excluding a protected
attribute did not prevent a disparate outcome.** On a real portfolio this would
block deployment pending investigation. A test asserts the check keeps flagging
something, so a future change cannot quietly weaken it and read as progress.

**On the 0.8 threshold** — it is the EEOC four-fifths rule from US *employment*
law, used because it is widely understood. It is not an insurance standard and
not a legal test for claims handling. See [`docs/AI_GOVERNANCE.md`](docs/AI_GOVERNANCE.md).

### Automation made this book more expensive, and the dashboard says so

Expense per claim went **up** +14.2% and mean cycle time went
**up** +2.3%. That is not a bug in the arithmetic — it is the
result of referring 27.1% of the book to investigation when the
all-manual arm investigates nothing at all. Total cost still falls
4.8%, but only once estimated leakage is counted.

The break-even is exact, because SIU time is the only term that scales with the
referral count:

- The automation saves **$184,369** against the manual arm before any
  investigation spend.
- Each referral costs **$1,100**, so the book can carry
  **167 referrals (16.8%)** before automation stops paying for
  the SIU programme on expense alone.
- This dataset forces **271 (27.1%)**, so the investigation programme costs more than the automation saves.

**That is a property of the dataset, not the design.** A 24.7% reported-fraud
rate is an order of magnitude above a real auto portfolio. At a realistic flag
rate the referral volume sits well under the break-even line. Quantifying that
is more useful than a headline saving would have been.

### The backtest is not evidence, and is labelled as such

The two arms are **paired**: the ClaimPilot arm is derived from each claim's own
baseline random draw by applying the route multipliers in
`config/assumptions.yaml`. Pairing removes sampling noise — the deltas are
stable and reproducible — but stability is not validity:

> Every delta in the table above is an **arithmetic consequence of the
> assumptions**, not a measured outcome.

A real backtest replays decisions against *observed* results. This one replays
them against *assumed* results, because the public dataset contains no handling
times, costs or leakage. The only measured figures in the backtest are the
routing mix and the SIU hit rate. The honest claim is "here is the operating
model, and here is exactly how its headline numbers fall out of its
assumptions" — and the weakest joint is named in the config: the manual arm's
fraud-miss rate is a flat assumption, while ClaimPilot's is derived from actual
routing, so the two are not like-for-like.

## ⚠️ Read these caveats before the numbers

- **The sample is tiny.** ~1,000 claims. Far too small to calibrate production
  thresholds.
- **The fraud rate is unrealistic.** 24.7% of claims carry the reported-fraud
  flag, roughly 10–25× a real auto portfolio. **Every threshold in this project
  would need full recalibration for a real carrier.**
- **The label is a proxy.** `fraud_reported` is a *reported* flag, not an
  adjudicated fraud finding. It inherits whatever bias the original referral
  process had.
- **Baseline savings are assumptions, not findings.** Handling times, costs,
  cycle times and leakage are simulated from documented assumptions. They show
  the *shape* of the business case, not evidence for it.
- **Geography and dates are narrow.** Losses cluster in Jan–Mar 2015 across a
  handful of states, so seasonality and state-by-state rules cannot be modelled.

### Two data traps worth knowing about

Both were found while building the ingest, and both are handled explicitly:

- **`injury_claim` is not an injury signal.** It is a near-mechanical ~12.5%
  slice of `total_claim_amount` and is non-zero on 97.5% of claims — *including*
  claims with zero reported injuries. Deriving an injury flag from it produced a
  99% injury rate and a useless triage feature. `has_injury` therefore uses the
  reported bodily-injury count only (66.0%).
- **`insured_hobbies` leaks the label.** A couple of hobby values correlate
  absurdly with the fraud flag in this dataset. It is excluded from every model
  input, so the fraud model is not flattered by an artifact.

## What's real and what's simulated

**Real** (from the published dataset): policy state, combined single limit,
deductible, annual premium, incident type / severity / date / location, bodily
injuries, witnesses, police-report availability, vehicle make / model / year,
injury / property / vehicle claim amounts, and the `fraud_reported` flag.

**Simulated** (generated by `scripts/simulate.py`, labelled 🧪 throughout the UI):
FNOL free-text narratives, mock policy terms, fictional policyholder contact
details, adjuster handling times, cycle times, costs, and claim deadlines.

Narratives are written **from each row's real field values**, and the values used
are retained as ground truth — so extraction accuracy can be *measured* against
the truth rather than asserted. Contact details are fictional by construction:
emails use the reserved `example.com` domain and phone numbers the reserved `555`
area code, so nothing is deliverable.

## AI governance

Designed around the **NAIC AI Model Bulletin**:

- **Human-in-the-loop by construction** — auto-approve is permitted, auto-deny
  is not, and this is enforced structurally rather than by convention. The
  `Destination` enum has no denial member, so a denial cannot be *represented*
  as a routing outcome; `config/routing_rules.yaml` declares an allow-list and
  a forbidden list, and the engine refuses to load a rules file containing any
  denial destination. Tests assert all of it, including an exhaustive pass over
  all 1,000 claims.
- **9 fields excluded from every model input**: `insured_sex`, `age`,
  `insured_education_level`, `insured_occupation`, `insured_relationship`,
  `insured_zip`, `insured_hobbies`, `policy_number`, `incident_location`.
  Outcomes are still tested across region, age band, vehicle category and sex.
- **Data minimisation** — personal data is masked *before* any text reaches an
  LLM. Masking happens in the provider base class, so no subclass can bypass it;
  a test proves it. The copilot additionally reads only a fixed allow-list of
  claim fields, so it cannot see the policyholder's demographics at all.
- **Every decision is justified and logged** — a denial cannot be *constructed*
  without a valid reason code and a substantive note. The guard is in the
  pydantic schema, not the form, so no code path can write an unjustified
  denial to the audit trail.
- **The reserve comes from a model, never from an LLM** — a test swaps in a
  provider that insists the reserve is $999,999,999 and asserts the suggested
  figure does not move.
- **Reproducibility** — one seed in `config/assumptions.yaml` makes every
  simulated table byte-identical across runs.

- **Outcome testing, not just exclusion** — STP and SIU rates are measured
  across region, age band, vehicle category and sex, with disparate impact
  ratios flagged below 0.8.
- **A model card per AI component** — purpose, data, inputs, exclusions, risk
  tier, owner, limitations and failure modes, in
  [`config/model_cards.yaml`](config/model_cards.yaml). Performance figures are
  read live from `metrics.json`, so a card cannot drift from its model.
- **Monitoring with a floor as well as a ceiling** — a near-zero override rate
  is treated as a warning, not a success: if humans never disagree with the AI,
  rubber-stamping is likelier than perfection.

The full programme summary, risk tiers, fairness approach and what a real
insurer would need beyond this demo are in
[`docs/AI_GOVERNANCE.md`](docs/AI_GOVERNANCE.md).

## How to run it

Requires **Python 3.11** (matching Streamlit Community Cloud).

```bash
make setup     # create .venv, install dev dependencies
make all       # download data, simulate, compute metrics
make run       # launch the app at http://localhost:8501
```

No API key is needed. With no key present, ClaimPilot uses its rule-based mock
and shows a **"Demo mode: rule-based AI"** badge; the app is fully functional
without one. To use a hosted LLM, copy `.streamlit/secrets.toml.example` to
`.streamlit/secrets.toml` and add your key — that file is gitignored.

## Deploy it yourself

The repo is designed for **Streamlit Community Cloud**: entry point at the root,
pinned runtime dependencies, Python 3.11, and every model and metric
precomputed and committed so the app does no training at boot.

### 1. Check before you push

```bash
make test          # full suite, including AppTest page smoke tests
make lint          # ruff
make check-deploy  # fresh venv, requirements.txt only, boot the app headless
```

`make check-deploy` proves the dependency set resolves and the server starts on
a clean environment; the AppTest suite proves every page actually renders. They
test different things — run both.

Confirm nothing sensitive is staged. `.gitignore` already covers `data/raw/`,
`.env`, `.streamlit/secrets.toml`, `.venv/` and caches:

```bash
git status --porcelain --ignored | grep -E "raw/|secrets.toml|\.env$"
```

That should list those paths as **ignored**, never as staged. Then scan the
tracked tree for anything key-shaped:

```bash
git grep -nIE "(sk-[A-Za-z0-9]{20,}|api[_-]?key[\"'\s:=]+[A-Za-z0-9_-]{20,}|BEGIN [A-Z ]*PRIVATE KEY)" -- . ':!*.lock'
```

No output means clean. `.streamlit/secrets.toml.example` is committed on
purpose — it contains placeholders only.

### 2. Create a public GitHub repo and push

With the [`gh` CLI](https://cli.github.com):

```bash
gh repo create claimpilot --public --source=. --remote=origin --description "AI claims triage, automation and governance demo for a fictional P&C auto carrier" --push
```

Or by hand, after creating an empty public repo in the GitHub UI:

```bash
git remote add origin https://github.com/<your-username>/claimpilot.git
```

```bash
git branch -M main && git push -u origin main
```

### 3. Deploy on Streamlit Community Cloud

1. Go to **[share.streamlit.io](https://share.streamlit.io)** and sign in with GitHub.
2. Click **Create app**, then **Deploy a public app from GitHub**.
3. Fill in the form:
   - **Repository:** `<your-username>/claimpilot`
   - **Branch:** `main`
   - **Main file path:** `streamlit_app.py`
4. Open **Advanced settings**:
   - **Python version:** `3.11`
   - **Secrets:** leave empty to run in demo mode. To use a hosted LLM, paste
     the contents of `.streamlit/secrets.toml.example` and fill in your key.
5. Set the **custom subdomain** — something like `claimpilot-<your-name>` gives
   you `https://claimpilot-<your-name>.streamlit.app`.
6. Click **Deploy**. First boot takes a couple of minutes while dependencies install.
7. Paste the URL into the **Live demo** line at the top of this README.

### If the deploy fails

The usual causes, in order of likelihood:

| Symptom in the Streamlit log | Cause | Fix |
|---|---|---|
| `ModuleNotFoundError` | A package used at runtime is only in `requirements-dev.txt` | Move it to `requirements.txt` and pin it |
| `FileNotFoundError: .../claims.parquet` | A data artifact was gitignored instead of committed | `git add -f data/sample/*.parquet models/*.joblib reports/metrics.json` |
| Build killed / out of memory | A heavy package crept in | Keep `requirements.txt` to the pinned ten; no LightGBM, no torch |
| App boots then errors on a page | A page imports something the runtime set lacks | Reproduce with `make check-deploy`, which uses runtime deps only |
| `Error installing requirements` | Python version mismatch | Set Python 3.11 in Advanced settings |
