# 🛡️ ClaimPilot — AI Claims Triage, Automation & Governance

**Auto insurance claims arrive faster than adjusters can work them. Triaging every
claim by hand is slow and expensive; automating payouts without controls invites
claim leakage and unfair outcomes.** ClaimPilot takes auto claims in digitally,
scores each one for severity, complexity and fraud signal, fast-tracks the simple
ones, assists adjusters with the rest, and makes every AI decision explainable,
fair-tested and auditable.

Built for the fictional carrier **Northwind Mutual**. `Intake → Triage → Route → Assist → Govern → Measure`

> 🚧 **Phase 1 of 5 complete** — data foundation, simulation layer and the
> PII-masked AI interface. Triage, workbench, governance views and the KPI
> dashboard land in Phases 2–5. The live link and screenshots go here once
> Phase 5 ships.

## The core tension

Three things pull against each other, and the whole product is about holding them
in balance:

| Pull | What it wants | What it breaks |
|---|---|---|
| **Speed & automation** | Pay simple claims in minutes, not weeks | Overpays claims nobody checked |
| **Claim leakage** | Scrutinise everything, pay only what's owed | Slow, costly, poor customer experience |
| **Fairness & compliance** | Consistent, explainable, non-discriminatory outcomes | Constrains how aggressively you can automate |

Two product rules fall out of that, and they are enforced in code:

1. **The system can auto-approve, but it can never auto-deny.** Every potential
   denial goes to a human. There is no code path to an automatic denial, and a
   test asserts it.
2. **Protected characteristics are never model inputs** — but outcomes are still
   tested across those groups, because excluding a field does not guarantee a
   fair result.

## ⚠️ Read these caveats before the numbers

- **The sample is tiny.** ~1,000 claims. Far too small to calibrate production
  thresholds.
- **The fraud rate is unrealistic.** 24.7% of claims carry the reported-fraud
  flag, roughly 10–25× a real auto portfolio. **Every threshold in this project
  would need full recalibration for a real carrier.**
- **The label is a proxy.** `fraud_reported` is a *reported* flag, not an
  adjudicated fraud finding. It inherits whatever bias the original referral
  process had.
- **Baseline savings are assumptions, not findings.** Handling times, costs,
  cycle times and leakage are simulated from documented assumptions. They show
  the *shape* of the business case, not evidence for it.
- **Geography and dates are narrow.** Losses cluster in Jan–Mar 2015 across a
  handful of states, so seasonality and state-by-state rules cannot be modelled.

### Two data traps worth knowing about

Both were found while building the ingest, and both are handled explicitly:

- **`injury_claim` is not an injury signal.** It is a near-mechanical ~12.5%
  slice of `total_claim_amount` and is non-zero on 97.5% of claims — *including*
  claims with zero reported injuries. Deriving an injury flag from it produced a
  99% injury rate and a useless triage feature. `has_injury` therefore uses the
  reported bodily-injury count only (66.0%).
- **`insured_hobbies` leaks the label.** A couple of hobby values correlate
  absurdly with the fraud flag in this dataset. It is excluded from every model
  input, so the fraud model is not flattered by an artifact.

## What's real and what's simulated

**Real** (from the published dataset): policy state, combined single limit,
deductible, annual premium, incident type / severity / date / location, bodily
injuries, witnesses, police-report availability, vehicle make / model / year,
injury / property / vehicle claim amounts, and the `fraud_reported` flag.

**Simulated** (generated by `scripts/simulate.py`, labelled 🧪 throughout the UI):
FNOL free-text narratives, mock policy terms, fictional policyholder contact
details, adjuster handling times, cycle times, costs, and claim deadlines.

Narratives are written **from each row's real field values**, and the values used
are retained as ground truth — so extraction accuracy can be *measured* against
the truth rather than asserted. Contact details are fictional by construction:
emails use the reserved `example.com` domain and phone numbers the reserved `555`
area code, so nothing is deliverable.

## AI governance

Designed around the **NAIC AI Model Bulletin**. Phase 1 ships the foundations:

- **Human-in-the-loop by construction** — auto-approve is permitted, auto-deny
  is not.
- **9 fields excluded from every model input**: `insured_sex`, `age`,
  `insured_education_level`, `insured_occupation`, `insured_relationship`,
  `insured_zip`, `insured_hobbies`, `policy_number`, `incident_location`.
  Outcomes are still tested across region, age band, vehicle category and sex.
- **Data minimisation** — personal data is masked *before* any text reaches an
  LLM. Masking happens in the provider base class, so no subclass can bypass it;
  a test proves it.
- **Reproducibility** — one seed in `config/assumptions.yaml` makes every
  simulated table byte-identical across runs.

The full programme summary, risk tiers and model cards arrive in Phase 4
(`docs/AI_GOVERNANCE.md`).

## How to run it

Requires **Python 3.11** (matching Streamlit Community Cloud).

```bash
make setup     # create .venv, install dev dependencies
make all       # download data, simulate, compute metrics
make run       # launch the app at http://localhost:8501
```

No API key is needed. With no key present, ClaimPilot uses its rule-based mock
and shows a **"Demo mode: rule-based AI"** badge; the app is fully functional
without one. To use a hosted LLM, copy `.streamlit/secrets.toml.example` to
`.streamlit/secrets.toml` and add your key — that file is gitignored.

### A note on storage

Streamlit Community Cloud resets its file system on restart. New claims and the
audit log live in `st.session_state` and are seeded with demo data, with a CSV
export button. **That storage is not permanent** — a restart clears anything
added through the UI.
